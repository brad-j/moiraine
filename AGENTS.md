# moiraine

The app for gaidin (`../gaidin`): a client of gaidin's HTTP API, built with TanStack Start in SPA mode and served by gaidin from the same origin. This repository is public.

## Commands

- `pnpm install`, then `pnpm check` and `pnpm e2e` before every commit. `pnpm check` builds, type checks, lints and runs the tests in `test/`, including the transcript test against gaidin's e2e server. `pnpm e2e` builds and runs the Playwright tests in Chromium, each against its own gaidin e2e server serving the build. Open a PR only with both passing.
- One test file while working: `node --no-warnings --test test/transcript.test.ts`, or `pnpm build && pnpm exec playwright test e2e/rules.spec.ts`.
- `pnpm dev:faux` runs the app against gaidin's e2e server: a scripted model, no keys, a throwaway data directory.
- gaidin must be checked out beside this directory (`../gaidin`, with its dependencies installed): the API types come from its `src/web.ts`, and the tests start its e2e server. For agents working through tower, `../gaidin` is gaidin's main and read-only.
- CI fails on any skipped test, so treat a skip as a broken setup. Tests never need a key or the network.

## Where things are

- Read gaidin's `docs/plan.md`, "Design: the app", before changing anything: it records what was decided with Brad and the order of work.
- The README's Layout section says where each part of the app lives.
- Look and feel follow `design.md`, the app's locked design system, with its tokens in `tokens.css`. Amend `design.md` rather than overriding it on one screen.
- `src/routeTree.gen.ts` is generated by the router plugin on build and dev; don't edit it.

## Rules

- moiraine is a client only. No server functions, server routes or SSR: gaidin is the server, and its HTTP API (`Gets`, `Posts` and `StreamEvent` in gaidin's `src/web.ts`) is the one interface.
- A change the app needs from the server is made in gaidin, in its own commit there. Working through tower you can't change `../gaidin`: say in the PR what gaidin needs, and stop.
- Import gaidin only with `import type` from `gaidin/src/web.ts`, through `src/api.ts`. Nothing of gaidin's may end up in the build.
- Borrow nothing from other assistants' apps, including names.
- A UI change comes with an e2e test that shows it working. Check UI changes in a browser against `pnpm dev:faux` when you can.
- The safety code is `scripts/ship.ts`, `public/sw.js`, `src/offline.ts`, `src/push.ts`, `src/api.ts` and `src/markdown.tsx`: the deploy, what's kept on the device, push, the boundary with gaidin, and the rendering of model output. A change that lets through anything these used to stop says so in the PR description and has a test. Never weaken or delete a test of them to make a change pass.
- Satisfy the lint rules by changing the code. Don't turn a rule off or add an ignore comment without saying why in it, as the existing ones do.
- Don't add or upgrade a package as part of a task; say in the PR that one is needed. pnpm resolves only versions at least 3 days old (`minimumReleaseAge: 4320`).
- Nothing about the owner's own setup goes in code, tests or docs: no real names, host names, LAN or tailnet addresses or home paths. The tests' user is `brad@example.com`; use `example.com`, `*.test` names and `192.0.2.x`.
- Commit messages describe the change in a sentence or more of prose, as the history does, with no `feat:`-style prefixes.

## Working through GitHub

- Work on a branch per issue, and put `Closes #N` in the PR description. Never push to main, and leave merging to Brad.
- The PR description says what changed, how you checked it, and anything you weren't sure of.
